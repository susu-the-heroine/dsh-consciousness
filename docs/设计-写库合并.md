## 决定：等锁策略怎么统一（2026-11-15 凌晨定，白天照这个做）

现状两条路：
- `store.js`（五十四处调用）：硬链接建锁（已对齐），等 0.8 秒，拿不到就**照写**并记 `write-lock-timeout`。
- `store-js.js`（网页与导入）：等 120 秒，拿不到就**拒写**并报错。

两个都不算错，错在**同一条链路里两种语义**：网页那边拒写会报错给人看，主链路这边照写会互相覆盖。

决定（按这个顺序改，每步都能独立回滚）：

1. **等锁时间统一成 3 秒**，都按 50 毫秒轮询。理由：一次写入 = 备份 + 写临时文件 + fsync + rename，
   实测在十几毫秒量级；3 秒是它的两个数量级余量，又不会让一次发言卡住超过三秒。
2. **拿不到锁时的行为，按"调用方认不认错"分两档**，不搞一刀切：
   - 认错的调用方（网页、导入、工具函数——它们能把错误显示给人）：拒写 + 返回具体原因。
   - 不认错的调用方（五十四处里的脚本与内部链路）：照写 + 审计（保持今天的行为）。
   等这些调用方逐个改成认错，再统一成拒写。**先改调用方，再收紧语义**，别反过来。
3. **缩水闸保持两条各自不变**（主链路"砍一半就拒"，网页"几乎清零才拒"）。
   收紧谁都得先有"读坏了"的实测样本，现在没有。

验收：
- `lock-interop-test.mjs` 两条路各写十次不坏（已有）。
- `write-race.mjs` 四进程并发不坏（已有）。
- 新增一条：人为占住锁 5 秒，主链路应在 3 秒后照写并留审计，网页那条应报"拿不到锁"。
  这条等第 1 步落地时一起写。

**没做的原因**：今晚已经动过写入链路两次（硬链接、缩水闸对齐），再改等待语义就是第三次，
且绕不开"调用方要不要认错"这个跨十个文件的改动。凌晨改数据链路，出事的代价是整库，不值。
