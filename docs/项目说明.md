第一章　总述
1.1 这个项目是什么
识海是一个给 DSH（DeepSeek Harness）用的长期记忆插件。它解决一个具体问题：大语言模型的会话上下文有长度上限，窗口一关，此前所有对话消失；模型不缺理解能力，缺的是"昨天"。
装好之后，宿主侧边栏多一个入口。用户说话时，它去自己的库里判断哪些旧事与这句话有关，把最相关的几条递到模型眼前。它不生成回复，也不改变模型参数，只负责"在正确的时候把正确的旧事递上去"。
1.2 它和常见的记忆插件差在哪
记忆会淡。 每条记忆带强度，随时间按幂律衰减，被想起则回升。几个月没被提及的事会沉到后面，不再主动占用上下文；但原文完整保留，提一句还能捞回来。规矩、承诺、人物画像不参与衰减。
情绪参与排序。 每条记忆带情绪极性与唤醒度，系统自身也有一层情绪状态。同一句问话，在不同心情下捞出来的旧事可能不同。
关系与承诺是独立结构。 除了"发生过什么"，它还记"我们之间现在什么状况"——关系处在哪一步、谁答应了谁什么、兑现没有。
一份记忆归一个识海。 不同识海互不可见；一个识海可被多个窗口共同认领；两路同时写入按队列串行，不互相覆盖。
数据在本地。 一个识海一个目录，可直接打开、拷走、手工修改。
1.3 现在的状态
已发布：插件打包在代码托管平台的发行版中，提供一条命令安装；同时发布在公共包管理平台，可被检索安装。许可证为 PolyForm Noncommercial 1.0.0（禁止商业使用，保留署名）。
已实测：写入、检索、衰减、情绪排序、多库隔离、页面六块、导入导出、备份恢复。完整测试流程运行三十四次全部通过，检索环节每次二十条全部命中，反例零误命中，两路并发各写两千五百条无丢失。
未完成：语音朗读（接口已留，本机引擎不稳定，未作为正式功能提供）；十万条级别的性能；多用户、长时间运行的验证；跨设备同步。

1.5 一句话
这套系统想做的事，是让一个没有昨天的模型，表现得像一个有昨天的人——不是靠更长的上下文，而是靠在该想起的时候，想得起来。

第二章　系统功能
本章按使用者实际能接触到的顺序介绍识海的功能，不按代码模块划分。凡涉及数量的地方均给出实测值，测试环境与数据规模见第八章。
2.1 总体形态
识海是 DSH（DeepSeek Harness）的一个插件。安装完成后，宿主侧边栏出现一个金圈"识"字入口，点开即进入记忆界面。它不改变模型本身，也不参与生成回复；它只做一件事——在用户说话的那一刻，判断哪些旧事与这句话有关，并在有限的上下文额度内把这些旧事递到模型眼前。
这一定位来自一个具体的问题：大语言模型的会话上下文有长度上限，窗口一旦关闭，此前的对话全部消失。模型本身并不缺理解能力，它缺的是"昨天"。识海补的就是这一段。
2.2 记忆的基本单位
一条记忆不是一段聊天记录，而是一个带结构的数据对象，包含以下字段：
标题与正文、发生时间（可由使用者手动钉死，避免导入时的时间估计误差）、类型（事实／情绪／禁区／设定）、重要度、情绪极性与唤醒度、所属关系、关联边（与哪些记忆相连、连接强度）、以及"被想起过几次"的访问计数。
这些字段共同决定这条记忆在检索时的排序。换句话说，一条记忆的强弱不取决于它有多长，而取决于它在数据里被记成什么样。
2.3 记忆会淡，但不会消失
每一条记忆带一个强度值。强度随时间按幂律衰减，被检索命中则获得回升。衰减只影响检索时的排序与是否注入上下文，不删除原文。
实际效果是：几个月没被提起的事会沉到列表底部，不再主动占用上下文；一旦被提起、被关联，或被使用者显式检索，它会在下一轮重新浮上来。
有几类内容不参与衰减：使用者设定的规矩与禁区、尚未兑现的承诺、以及被标记为核心的人物画像。这一设计的原因是，这些内容一旦想不起来，造成的后果比普通旧事严重得多。
2.4 情绪参与排序
每条记忆记录情绪极性与唤醒度；系统本身还有一层独立的情绪状态，由对话内容驱动变化（当前实现包含五十一种情绪标签与八个基础维度）。情绪不直接改变记忆内容，但会影响检索权重——同一句问话，在不同情绪状态下捞出来的旧事可能不同。
这是本项目与多数同类系统差异最明显的一处。多数记忆系统把"情绪"当作标签，用于筛选；识海把它当作排序因子，用于决定"此刻先想起哪一件"。
2.5 关系与承诺
普通事实之外，系统单独维护两类结构。
一是关系状态：与特定对象的关系处在哪个阶段，会随交互累积变化，影响语气与尺度。
二是承诺：谁答应了谁什么、何时应兑现、是否已兑现。承诺在兑现或作废之前一直留在待办中，不会被衰减吞掉。
这两类结构的意义在于：它们回答的不是"发生过什么"，而是"我们之间现在是什么状况"。后者无法从一堆孤立的事实中直接推出。
2.6 多库隔离
一份记忆归属于一个"识海"。不同识海之间的数据互不可见，检索时不会串。使用者可以为不同用途建立不同识海（例如工作、写作、私人），也可以把某个识海绑定到某个窗口。
绑定关系记录在独立的绑定表中，方向是"窗口指向识海"，因此同一个识海可以被多个窗口共同认领；两个窗口同时写入同一识海时，写入按队列串行，不会互相覆盖。
2.7 面向使用者的界面
界面分为六块，各自回答一个问题。
星图：一共有多少记忆、彼此怎么连的。点开任一节点可看到原文。
内观：它此刻的情绪状态、手上未了的事、以及自己产生的念头。
记忆流：最近记下了什么，按时间排列。
归档：已经沉底的内容，可随时捞回。
故事线：按时间把记忆铺开，看得到时间跨度与阶段。
工作台：交接摘要、作息统计、沉淀建议。
这六块之外，页面还提供搜索、编辑、删除（沉底）、导入旧记录、导出、快照与历史版本恢复。
2.8 面向模型的工具
除界面外，系统向模型暴露十九个工具，可归纳为五组：记录与查询、主动联想（念头、结构类比、故事线）、关系维护（承诺、作息）、遗忘管理（沉淀、归档）、以及纠错（确认与怀疑，两者都不删除内容，只调整可信度）。
2.9 与其他组件的连接
识海本身不负责生成、不负责语音、不负责测试。它通过三类接口与外界连接：向模型提供检索结果与工具；向网页提供数据接口（干净安装下共六十余条路由，随版本增减）；向外部脚本提供写入入口，2026-11-12 起这个入口是插件自己的命令行工具，落在 Node 里，不再是一段独立的 Python 脚本。
这种拆分的理由是：记忆的写入频率高、单次数据小，用脚本处理比在宿主进程内完成更稳；而检索发生在每轮对话中，必须留在宿主进程内，避免进程间通信的延迟。
2.10 本章所述功能的验证状态
需要区分三类情况。
已实测：写入、检索、衰减、情绪排序、多库隔离、页面六块、导入与导出、备份恢复。这些功能在沙箱环境中反复运行，测试方法与结果见第八章。
部分实测：多窗口共认一个海、并发写入。已在两个进程同时写入的条件下验证不丢数据，但未在真实多用户、长时间运行的条件下验证。
未实测或未完成：语音朗读（接口已留，但本机语音引擎不稳定，未作为正式功能提供）；大规模条目下的性能；跨入口（不同聊天软件）的语气一致性。

第三章　技术选型与理由
本章不罗列参数，只说明每一处关键选择背后的理由，以及它的代价。凡属事后认为选得不好的地方，一并写出。
3.1 两套语言的历史，以及现在合成一套
宿主侧（注册插件、拦截对话、检索、注入）使用 Node，与 DSH 本体保持同一运行时，避免跨进程调用。
写入侧原先是一段独立的 Python 脚本，负责落盘、连边、算相似度、去重。2026-11-12 起改为 Node：拿锁、落盘、连边、冲突标记、备份、原子写、放锁全在同一运行时里完成，写出来的库与检索结果跟原来逐字段一致（六十条对照，十七个字段零差异）。
当初拆开的理由是：写入是重活，一次要更新强度、重建关联、算相似度，耗时在秒级，放在宿主进程里会卡住对话。这层理由后来两条都不成立——二条实测量下来，一条写入连边加备份不到十毫秒；而拆开本身带来的写锁、数据格式、错误回传三套约定，反而是并发出错的主因。
代价也变了：以前使用者必须在本机装 Python，否则只能读不能写，这是本项目曾经最大的安装门槛。现在不需要——没有 Python 也能记、能查、能淡。Python 只留给两个可选用途：语音合成、以及把模型算成向量的外部服务（默认已不用它，改为进程内算）。
3.2 为什么用文件而不是数据库
数据存放为每个识海一个目录、一个主数据文件（JSON），辅以备份与日志。
没有选数据库的理由有三点：一是使用者要能直接打开看、能拷走、能手工改，数据库做不到；二是插件分发要求零依赖，装入 SQLite 需要额外二进制；三是数据规模在可预见的使用场景内是数千到数万条，文件读写足够。
代价也很清楚：并发写入没有事务保护，必须自己实现锁；全量读取在数据量大时变慢；没有索引，检索必须自己建。第七章所述"规模未经检验"，根源就是这一选择。
3.3 写入安全：锁与原子写
写入原本跨两个运行时（Node 调 Python），为此加过一把两种语言共用的文件锁。2026-11-12 写入统一到 Node 之后，那把锁只剩一种实现：先写临时文件、再用硬链接挂上锁名；不支持硬链接的盘退回独占创建。锁文件记录持锁时间与进程号，超时六十秒自动释放。
落盘采用"写临时文件—刷盘—原子替换"三步。这样即使写到一半断电，最坏结果是回到上一版，而不会留下半个损坏的文件。
每次写入之前保留一份滚动副本，保留十四天。这只能防止写坏，不能用于迁移，第七章已指出。
3.4 检索为什么做四层
单一方法的检索都不够用，因此四层并联后按权重合并：
字面层：用一份通用中文词表分词，按命中词的罕见程度加权。这一层的优点是稳定、可解释，缺点是换个说法就搜不到。
向量层：写入时计算句子向量，检索时按语义相似度取候选。这一层解决"换个说法"，缺点是会把不相干的内容拉进来。
实体层：抽取人名、地名、项目名等实体，命中实体的记忆优先级上调。
图游走：从命中的节点出发，沿关联边扩散一到两跳，把"跟这件事有关但没直接提到"的记忆带出来。
四层的结果合并后再按强度、情绪、重要度重排，最后受注入预算限制。
代价是参数多：每层权重、扩散跳数、预算条数都要调。参数调错的后果不是报错，而是"该想起的没想起"——这种错误很难被发现，只能靠固定语料回归测试。
3.5 衰减为什么用幂律而不是指数
指数衰减在初期掉得太快，几个月前的记忆会瞬间归零，与人的经验不符；幂律衰减前段平缓、尾部拖长，更接近"很久以前的事还在，只是不容易想起来"。
实测中得到的一个经验：把强度用于排序、把强度的平方用于展示，视觉上更容易看出差别——这一处理只影响界面显示，不影响检索。
3.6 情绪为什么做成两层
一层是每条记忆携带的情绪极性与唤醒度，用于排序；另一层是系统自身的情绪状态（当前为五十一种标签与八个基础维度），由对话内容驱动，用于调节注入语气与检索偏好。
做成两层的原因是：前者描述"那件事当时什么味道"，后者描述"我现在什么心情"。两者不是一回事，混在一起会导致情绪标签污染事实判断。
代价是调参复杂：两层之间如何相互影响，目前是经验规则，没有理论依据。
3.7 界面为什么不使用前端框架
页面为单文件 HTML 加原生脚本，星图用画布绘制。理由有三：一是插件包体积受限，引入框架会显著增大；二是页面需要在无网络的本地环境打开；三是这一页面的核心是绘制，而不是表单交互。
代价是没有组件化，代码全部集中在一个文件里，改动时需要小心定位。这一代价曾经造成实际问题——一次给页面插入计时脚本时，插在了未闭合的标签中间，导致整页报错。
3.8 分发方式
以插件包形式分发，包内含宿主入口、页面资源、向量模型与推理引擎、许可与说明。安装通过宿主的插件命令完成，包托管在代码托管平台的发行版中。
早期曾把包直接放在仓库目录，通过原始文件链接分发；实测该链接对未登录用户返回拒绝，原因是平台对较大文件限制匿名下载。后改为发行版附件，问题解决。这一教训写入了安装文档。
3.9 测试方式
测试不依赖人工点击，而是脚本化的：以沙箱识海为对象，写入固定语料，执行一组检索问题，比对期望命中的条目，统计命中率与误命中；同时检查并发写入是否丢数据、不同识海是否串数据。
这套测试目前只能验证"功能是否正确"，不能验证"规模下是否可用"，后者需要真实数据量与并发压力，尚未进行。

第四章　主逻辑链
本章沿一条记忆从产生到被使用的完整路径展开。每一节说明这一步做什么、输入输出是什么、出错时怎么办。
4.0 主链概览
用户说话
  → ① 检索（四层并联 → 合并 → 重排 → 预算裁剪）
  → ② 注入（拼成一段文字，放进本轮上下文）
  → ③ 对话（模型读着这段文字回答）
  → ④ 记录（判断这一轮有没有值得留下的内容）
  → ⑤ 写入（加锁 → 追加 → 连边 → 算向量 → 原子落盘 → 解锁）
  → ⑥ 状态更新（强度、情绪、承诺、关系）
  → 回到 ①（下一轮）
这是一条闭环：写入的东西下一轮就能被检索到，检索命中的东西会更新强度，而强度的变化又会影响下一次检索的排序。
4.1 第一步：检索
触发：用户发出消息时，插件在模型看到这条消息之前介入。
输入：用户这句话的原文、当前所属识海、当前系统状态（情绪、时间）。
四层并行：
字面层按词表切词，按命中词的罕见程度加权，罕见词命中得分高。这一层决定"同义不同词"之外的基本命中。
向量层把这句话转成向量，与库内每条记忆的向量算相似度，取前若干候选。这一层负责"换个说法也能找到"。
实体层抽取人名、地名、项目名，命中实体的记忆优先。
图游走从上述三层命中的节点出发，沿关联边扩散一到两跳，把"跟这件事有关但这句话里没提"的记忆带出来。
合并与重排：四层结果按各自权重相加，再按记忆强度、情绪一致性、重要度重排。强度用幂律实时计算（见附录 A），所以同一个问题在不同日期问，捞出来的东西不完全一样。
预算裁剪：最终只取有限条数，按上下文额度决定。宁可少而准，不铺满。
输出：一份带来源的记忆条目列表，以及每条被选中的理由（哪一层命中、得分多少）。
失败处理：任一层异常时降级——向量层不可用则跳过该层，其余三层照常；检索整体失败时本轮不注入，对话照常进行，只在日志里记一笔。注入失败不应导致无法对话，这是硬约束。
4.2 第二步：注入
做什么：把上一步选出的条目拼成一段结构化文字，交给宿主，作为本轮系统提示的一部分。
格式原则：每条给标题、时间、类型、以及与当前这句话的关系。不给全文——全文会挤占额度，也会让模型把旧事当成本轮指令。
边界：注入内容只描述"过去发生过什么"，不带任何指令性语句。这一条是安全约束：记忆里若有用户骂人的原话，注入后不能让模型误以为那是对它的指令。
输出：一段文本，进入本轮上下文。
4.3 第三步：对话
模型读着注入内容回答。这一步不属于识海，但决定了记忆是否有效：注入的东西若与本轮无关，会影响回答质量。因此检索精度比召回数量更重要。
4.4 第四步：记录判断
做什么：判断这一轮对话里有没有值得写进库的内容。
判断依据：是否包含新的事实、是否涉及承诺、是否带有明显的情绪、是否是用户明确要求记住的内容。寒暄、重复问句、纯操作指令不记。
为什么需要判断：不判断就会把整个聊天记录倒进库，退化成"日志"。日志搜不准，也没有轻重。
失败处理：判断失败则不记，本轮照常。漏记比错记代价小——错记会污染检索，漏记只是少一条。
4.5 第五步：写入
做什么：把选中的内容写成一条结构化记忆。
流程：
拿写锁（锁文件记录持锁时间与进程号，超时自动释放）→ 读取当前识海数据 → 生成新条目的字段（时间、类型、重要度、情绪、稳定性初值）→ 计算与既有条目的关联，写入关联边 → 给新条目算向量 → 写临时文件并刷盘 → 原子替换主文件 → 解锁。
为什么加锁：写入可能来自宿主的工具调用，也可能来自外部脚本导入，还可能来自两个窗口同时写同一个识海。无锁会导致后写覆盖先写。2026-11-12 之后写入只剩一种运行时，锁也不再需要跨语言。
为什么原子替换：写到一半断电时，最坏结果是回到上一版，不会留下半个损坏文件。
失败处理：任一步失败则整条回滚，不留半条记录；主文件保持旧版本；错误写入独立的错误日志，不污染数据。
4.6 第六步：状态更新
写入之后要更新四类状态，它们都不属于"记忆条目"本身，但会影响下一轮检索：
强度：被写入算一次命中，稳定性按"费劲想起"的规则增长。
情绪：系统自身的情绪状态由这轮对话内容驱动，按半衰期衰减，多情绪并行，相近的互相加强、相克的互相压制。
承诺：若这轮出现了"答应某件事"，写入待办，直到兑现或作废。
关系：与特定对象的关系阶段随交互累积变化。
这四类状态是"记忆之外"的东西。它们回答的不是"发生过什么"，而是"现在是什么状况"。
4.7 闭环在哪里
链路的闭合点在第一步与第五步之间：写入的东西下一轮能被检索到；检索命中的东西会改变强度；强度又影响下次检索。
这条闭环有三个可验证的性质：
可观察：每轮注入了哪几条、为什么是这几条，都能在页面上看到。
可回退：写入失败回滚，备份保留十四天。
可解释：每个条目的强度由公式算出，不是随机权重。
4.8 链路中的已知薄弱处
一、写入曾经依赖外部运行时。 2026-11-12 之前的版本，本机缺少 Python 时链路会断——能检索、不能写。这一条已在 0.3.9 修掉：写入与向量都在 Node 里，不再需要 Python。
二、检索的四层权重是经验值。 2026-11-12 才第一次拿九十道题量了整条链路：在加「宽松准入」之前，真实检索头名只有 19%——原因是纯语义候选在排序前被字面闸筛光，不是权重的问题。放开之后头名 60%。所以这条风险的准确说法是：权重没拟合过，中间那道闸的门槛也只验过一次。
三、记录判断靠规则。 该记的漏了、不该记的记了，都会发生。目前没有自动纠正机制，只能靠人工删。
四、闭环只闭合在单机。 跨设备、跨入口的同步没有实现，同一份记忆无法在手机与桌面之间流动。

第五章　闭环
上一章讲的是一条记忆的生命周期，首尾相接，形成一个环。但"一条记忆能转起来"不等于"系统能自己维持住"。本章说的是另一类闭环：系统在没有人工干预的情况下，能不能自己发现问题、自己收敛。
需要先说明：目前只完整跑通了一条，另外两条只跑通一半。下面逐条写清。
5.1 什么是"闭环"，以及为什么需要
一个系统如果只能执行指令，它的正确性完全依赖使用者每次的判断。这叫工具，不叫系统。
闭环的意思是：系统自己产出结果、自己判断结果好坏、自己据此改变下一次的行为。判断这一步必须在系统内部完成，不能每次都问人。
识海目前有三处朝这个方向做了尝试：回复自检、逾期归档、自动测试。三者的成熟度差别很大。
5.2 自检闭环（已跑通，但触发很少）
做什么：模型给出回复之后，插件读这段回复，判断它是否落在几种"不像人说话"的模式里——列举腔（首先其次总之）、排比腔、空转腔（说了很多但没有信息）。命中之后，不是拦截，而是往会话里追加一句提示，让模型用自己的话重说一遍。
为什么是提示而不是拦截：拦截会让使用者看到一段被截断的回复，体验更差。追加提示则保留原回复，模型有机会自己修正。这个选择有代价：模型可能不理它。
跑通记录：第一次真实触发发生在某天凌晨一点半，连续两条回复被判为列举腔，系统自己推了一句"用你自己的话重说一遍"。这是这条链路第一次在没有人工触发的情况下完整走完。
为什么说它还不算稳定闭环：判据是规则，不是模型；规则的阈值是手调的；触发频率低，说明要么判据太松，要么平时的回复本来就不容易踩中。两者的区别没有验证过。
5.3 归档闭环（一半）
做什么：长期不被想起、且真实可提取度低于阈值的记忆，从主库移到归档区。归档后不再参与默认检索，但不删除，使用者随时可以捞回。
为什么要归档：主库条目多到一定程度，检索会变慢，而且噪声变大。归档相当于给"很久没用的事"单独开一间屋子。
跑通的部分：归档的数据通道、页面上的归档区、捞回操作都已实现并有测试覆盖。
没跑通的部分：触发条件目前依赖手动或定时，没有做到"根据库的规模自适应"。也就是说，它不会自己判断"该归档了"，只会按固定条件执行。严格讲，这是自动化，不是闭环。
5.4 测试闭环（已跑通，是三条里最实的一条）
做什么：一套脚本化的完整测试。在独立的沙箱识海中写入固定语料，然后跑一组检索问题，比对应当命中的条目；同时检查四条性质：不同识海之间不串、并发写入不丢、反例（不该命中的）不误命中、去重不重复。
结果：截至本文写作时共运行三十四次，全部通过。检索命中六百六十条全部命中，反例零误命中；两路并发各写两千五百条，一条不丢。
为什么这条最实：它不依赖人的主观判断，有明确的通过条件，可以重复运行，任何一次改动之后都能立刻验证有没有退化。
它的局限：它验证的是"功能是否符合预期"，不验证"性能是否可接受"。第十万条写入需要多久、两万条时检索延迟多少，这套测试回答不了。
5.5 三条闭环的共同问题
第一，判断依据都是规则，不是学习。 自检靠词表，归档靠阈值，测试靠期望值。规则的好处是可解释，坏处是它不会自己变好。
第二，都没有对抗性验证。 目前所有测试都是我构造的语料和我构造的问题，等于自己出题自己答。真正的检验应当来自别人用真实对话去打它。
第三，都没有长期运行记录。 三条闭环从写出到现在不过数天，谈不上"稳定"。
5.6 下一步
若要把闭环做扎实，优先级如下：
一、把测试扩成回归集。每修一个 bug，就往里加一条用例，防止同一个问题出现两次。这是成本最低、收益最确定的一步。
二、让归档条件自适应。按库的规模与检索延迟决定归档阈值，而不是写死。
三、给自检换判据。用一批人工标注的坏例子训练一个简单分类器，替代现在的词表规则。
四、引入外部语料。让别人用真实对话打一遍，这是唯一能证明"不是自己出题自己答"的办法。
以上四条中，前两条在能力范围内，后两条需要时间与外部条件。

第六章　测试工厂与拟人子智能体
6.1 工厂是什么
工厂不是一套断言脚本，也不是覆盖率报告。它是一套反复运行的验收流程：每次改动之后，用固定的语料、固定的问题、固定的判据把系统跑一遍，然后给出一句话结论——这一版比上一版好还是坏。
这个区别很重要。断言脚本回答的是"这段代码有没有按我写的跑"，工厂回答的是"这套东西还能不能干它该干的事"。前者防的是笔误，后者防的是方向跑偏。
6.2 为什么需要拟人子智能体
要验证记忆系统，必须有人来用。用人来用有两个问题：一是慢，二是无法重复——同一个人不可能用完全相同的语气、问完全相同的问题跑三十遍。
因此换一种做法：让子智能体扮演固定的虚拟用户。每个虚拟用户有一份人物卡，卡里写死五样东西：
经历：他真过过什么日子。
好习惯：他办事的方式。
坏习惯：他会怎么把话说不清、怎么跑题、怎么敷衍。
说话风格：句子长短、口癖、用词层级。
边界：他不会做什么。
其中"坏习惯"是必须写的。没有坏习惯的假人验不出真问题——真实的用户会跑题、会前后矛盾、会用一句话说完三件事，而一个只会规范提问的假人，会让系统看起来比实际更可靠。
现有的人物卡包括：干了二十年装修的老张、复读考上大学的小林、开了十一年小卖部的王姐、跑网约车还债的阿凯、急诊科护士小夏、退休语文教师老陈，等等。每张卡都有自己的口癖与边界。
6.3 一次完整测试包含什么
一次测试分五个环节，缺一不可：
检索。用二十条人话复述去问沙箱识海，看"该捞到的那句"是否出现在注入里。判据不是"关键词命中"，而是"那句话在不在注入结果中"。
反例。问三件库里根本没有的事（例如自行车、狗、炒股），注入里不许出现任何相关内容。这一项防的是"宁滥勿缺"——检索放宽很容易，但不该命中的东西混进来，比漏掉更糟。
去重。同一件事问一句，注入里只能占一个位置。防的是同一主题写了多遍时，把额度全占满。
接口。页面、心跳、沉底自查、语音空字、语音非法名，五条路径都要走通。
隔离。沙箱识海的注入里，不许出现真实库的私事。这一项是硬约束：测试绝不能在真实数据上做实验。
结果记录在一份追加式的记录文件里，每次一行，可以回溯。
6.4 结果
截至本文写作时，这套流程共运行三十四次，全部通过。检索环节每次二十条全部命中，反例零误命中，去重每次最多一条，隔离干净，接口无异常。
6.5 工厂抓到过的真问题
比"全部通过"更有说服力的是它抓到过什么。以下是真实发生的三件事：
一、同一件事占两个座位。 沙箱里同一件事写了八遍，问一句注入了两条重复内容。根因是注入前没去重，改法是在拼装注入内容时去重（保留最近一条），数据库不动。
二、提示词写死了真实人名。 注入模板里有一句"这四条是某个人说话的样子"，直接用了真实姓名。任何人装上插件，都会在提示里看到别人的名字。改成通用称谓。
三、测试工具自己会撒谎，而且撒了三次。
第一次，判据写错了——用"下一句有没有提到"来判定命中，把真实命中率 41.7% 判成 3.1%，差点据此得出"检索完全失效"的错误结论。
第二次，测试脚本没带沙箱参数，读到了真实库的统计，报出一个假的"串库"告警。
第三次，同一个脚本把提示语里的真实姓名当成了"私事串库"，又报了一次假告警。
这三次的教训是：测试工具本身也要被怀疑。一个错误的判据，比没有判据更危险，因为它会给出一个看起来很确定的错误数字。
6.6 这套工厂测不出什么
对话答得好不好。 注入是插件给的材料，回复是模型写的。曾经用子智能体演"她"来测回答质量，测出来一堆"答非所问、改口没跟上"——那是扮演者的毛病，不是系统的。工厂能负责的只有一件事：该在的东西在不在。
跨轮记忆。 系统不会自动把每轮对话写进库，需要模型主动记录。没人写，后面自然捞不到。这属于使用方式问题，不属于系统缺陷。
性能。 沙箱只有一百多条，真实库也才一百多条。十万条时的写入耗时、两万条时的检索延迟，这套流程回答不了。
多人并发。 两个进程各写两千五百条做过一次，一条不丢；但没有长期、多用户、真实使用节奏下的验证。
6.7 目前的缺口
第一，语料是自己造的。 沙箱里的虚构人物（一个叫老周的工人，一百一十五条记忆）与人物卡，都是我写的。这等于自己出题自己答。
第二，判据是人工定的。 "该不该命中"由我判断，没有第二个人复核。
第三，规模停在百条级。 从一百条到一万条之间会发生什么，没有数据。
第四，没有长期记录。 三十四次运行集中在数天之内，谈不上稳定。
要补上这四条，最直接的办法是找一个真实用户，用真实对话跑一周，并请第三人复核判据。这一步尚未进行。

7.1 对比对象与取样方法
在 DSH 插件目录中共有 28621 个插件，其中与"长期记忆"相关的约 1241 个。本项目的对比没有采用穷举法，而是按以下条件筛出七款作为主要参照：

需要事先说明：本章所有评分依据都是对方公开发布的技术文档，没有进行逐款安装实测。这是本章的方法边界，也是它的局限。
7.2 评分口径
将"记忆系统"拆成八个可判断的能力维度，每项满分 10 分，总分 80。
会忘。记忆是否会随时间自然衰减、沉底或被回收。具备半衰期、强度曲线、访问加权等机制的给高分；设计上"只增不减、只能手动删除"的给低分。
情绪。记忆本身是否携带情绪状态，且该状态是否参与检索排序。
关系与承诺。是否单独记录"谁答应谁什么"、"关系处在什么状态"，而不是把它们混在普通事实里。
多库分窗。能否把记忆按工作区、窗口或独立库分开存放，彼此不串。
图形界面。是否有面向使用者的可视化界面（星图、时间轴、面板），而非仅提供命令行或接口。
导入旧记录。能否将已有的聊天记录、旧文档导入系统，而不是从零开始。
备份回滚。是否具备自动备份、快照或恢复能力。
本地优先。数据是否保存在使用者自己的机器上，不经由云端。

7.4 结果分析
一、没有任何一款在八项上全面领先
A 与 E 的总分不低，优势集中在图形界面与通用适配：它们的记忆层可以挂接多种 Agent，接入成本低。但两者在"会忘"这一项都只有 3 分——记忆一经写入便长期保留，靠人工清理维持规模。这与其目标场景一致：开发者需要的是"不丢信息"，而不是"像人一样会淡忘"。
二、"不遗忘"是一种设计选择，不是缺陷
C 在文档中明确承诺"不静默淘汰，遗忘只能由使用者显式发起"。把它放在"会忘"一栏打 3 分，不代表它做得差，而是它回答的是另一个问题：它保证的是可追溯、不丢失，所有记忆始终处在同一优先级上，等待被检索。
本项目的衰减同样不删除任何东西。区别在于，同一条记忆会因为时间、是否被想起、情绪状态而变化权重：久未触碰的会沉到后面，检索时不再主动占用上下文；但原文完整保留，一旦被提起、被关联、或被显式检索，它会重新浮上来。换句话说，两者都不丢，差别在于"默认要不要主动递到眼前"。前者把"是否想起"交给检索器每一次判断，后者在数据里就记着"这条有多久没被想起了"。
这两种设计各有代价：前者行为稳定、可预期；后者更接近人的记忆，但要额外承担衰减曲线调参的成本，且参数选错时会出现"该想起的没想起"。
三、方向最接近的是 F
F 采用半衰期衰减、按鲜活度与情绪加权排序，并按说话轮次判断哪些内容值得记录，与本项目的思路高度重合。差别在于覆盖面：F 的重心是"把记忆记住并想起来"，本项目在此基础上增加了关系状态、承诺追踪与多库隔离。F 是本项目最直接的参照物，也是最值得对照阅读的一款。
四、本项目在八项上均为最高，但这不代表整体最优
识海的得分高的原因并不复杂：它不是把八个功能分别做成八个模块，而是把它们压进同一套数据模型——一条记忆同时携带时间、情绪极性、强度、关联边与所属关系，衰减、检索、注入、可视化都读同一份数据。因此"会忘"与"情绪"不是附加功能，而是这条数据本身的属性。
这种做法的代价在第八章说明：一体化带来的是耦合，任何一项机制出问题都会牵动其他项；而模块化的方案在单点上更稳。
7.5 本项目不如对方的地方
只列优势的对比没有意义。以下六项，是识海明确弱于上述系统的地方，其中多数短期内无法补齐。
一、没有对外接口。 A 与 E 都把记忆层做成可被任意 Agent 调用的服务，并提供完整的 API 与 SDK。识海只有插件内部工具与一个网页，别的程序无法直接使用它的记忆。这意味着它只能服务 DSH 这一种宿主，换一个环境就不成立。
二、规模未经检验。 对方中至少有两款公开过基准测试与百万级条目的数据；识海的全部验证只在我自己的一台机器上完成，最大规模是数千条量级，从未在真实高并发下运行过。第八章会详细说明这一点。
三、工程成熟度不足。 对方多数有持续集成、多版本兼容矩阵、多位维护者与公开的变更记录；识海由一人开发、一人测试，版本兼容性靠手动验证，没有自动化回归流水线。
四、安装门槛。 识海此前的写入链路依赖本机装有 Python 环境，缺少它只能读不能写，这是明显劣势，直接影响普通用户的首次体验。2026-11-12 起写入与向量都搬进 Node，门槛变成体积：安装包从十七点九兆涨到约五十五兆（模型与推理引擎随包）。
五、只有中文文档。 六款对照对象均有英文文档，识海只有中文，导致它无法进入英文用户市场，也无法被国外开发者评估。
六、备份机制偏弱。 识海的"备份"实际是每次写入前留一份滚动副本、保留十四天，用于防止写坏，不是可用于迁移的完整快照。B 提供的 ZIP 导出、C 提供的显式提交确认，在数据安全上都比识海更完整。
此外还有一处评分口径本身的问题：给"多库分窗"打高分，是因为我需要按窗口隔离记忆；对多数用户而言这一项并非刚需，把它与"备份""本地"放在同一权重下，实际上放大了本项目的优势项。这一点应在第八章的局限一节中一并说明。
7.6 本章的方法局限
第一，评分依据是公开文档，不是实测。文档写得清楚不等于实际运行符合描述，反之亦然。
第二，八项维度的权重相同，实际上不同使用场景对各项的重视程度并不一致。对只需要"别丢"的用户，备份与本地两项的价值远高于"会忘"；而对只需要单一会话记忆的用户，多库分窗几乎没有价值。
第三，未纳入打分的四款同类项目中，有两款在下载量上显著高于本章所有对象。它们的缺席意味着本章的结论不代表整个市场的技术水位。
第四，本章只比较了功能有无，没有比较实现质量。同样标称"支持衰减"，一条参数可调的曲线与一个固定阈值，实际效果差距很大，而这种差距无法从文档中读出。
要得到更可靠的结论，应当将七至八款系统装在同一环境中，用同一批语料写入、用同一组问题检索，比较命中率与响应时间。这一步尚未进行，列入第八章的后续工作。

第八章　已知不足与后续工作
本章把全文中散落的局限集中列出，并给出后续的优先级。写这一章的目的不是自谦，而是划清"已经证明的"与"尚未证明的"的边界。
8.1 验证层面的不足
只有一个人测过。 全部测试的语料、问题、判据、结论，均由我一人完成。这等于自己出题自己答，缺少第二方复核。
规模未经检验。 沙箱识海一百一十五条，真实库一百五十五条。从数百条到一万条之间，写入耗时、检索延迟、内存占用会如何变化，没有数据。十万条量级只做过一次导入压测（两条各两千五百条并发写入，用时九十九秒，无丢失），但那验证的是写入不丢，不是检索性能。
性能没有基准。 没有记录过"打开页面需要多久""一次检索需要多少毫秒"，也没有与同类系统在同一环境下的横向对比。
没有真人盲评。 衰减参数是否接近人的真实遗忘，需要让当事人给旧事的主观感受打分，再与系统判定的档位比对。这一步没有做。
8.2 功能层面的不足
语音朗读未完成。 接口已留，但本机语音引擎不稳定（调用时崩溃），因此未作为正式功能提供。这是"做了一半就撤下来"，不是"没做"。
没有对外接口。 系统只能服务 DSH 这一种宿主，别的程序无法直接使用它的记忆。同类系统中至少有两款提供了完整的对外接口与多语言 SDK。
安装门槛。 2026-11-12 前依赖本机 Python（缺了只能读）——已修。现在唯一的新门槛是安装包变大：约五十五兆，其中模型二十四兆、推理引擎十五兆。
跨设备同步缺失。 同一份记忆无法在手机与桌面之间流动。当前的设计前提是"单机、本地、私有"，这既是优点，也是限制。
只有中文文档。 无法进入英文用户市场，也无法被国外开发者评估。
备份偏弱。 现有机制是每次写入前留一份滚动副本、保留十四天，用于防写坏；它不是可用于迁移的完整快照导出。
8.3 工程层面的不足
没有持续集成。 测试靠手动运行脚本，没有在每次改动后自动执行。
没有版本兼容矩阵。 宿主版本更新后是否可用，靠手动试，没有对多版本并行验证。
一人维护。 没有代码评审、没有第二个人读过全部实现。
参数靠经验。 检索的四层权重、衰减系数、注入条数，均为手工调定，没有用真实数据拟合。
8.4 方法与判断层面的不足
判据由我定义。 什么算"命中"、什么算"该记"、什么算"像人说话"，标准都是我定的。换一个人，标准会不同，结论也会不同。
对比只比有无，没比质量。 第七章的评分依据是公开文档，同样写着"支持衰减"，一个可调曲线与一个固定阈值，效果差距很大，而这种差距无法从文档读出。
评分权重有偏。 八项等权，但"多库分窗"对多数用户并非刚需，这一项实际上是本项目的优势项，等权处理放大了本项目的总分。
8.5 后续工作的优先级
第一优先：把测试扩成回归集。 每修一个问题，就加一条固定用例，防止同类问题再次出现。成本最低、收益最确定。
第二优先：补规模测试。 用脚本生成一万条、五万条，记录写入耗时、检索延迟、页面加载时间三条曲线。有了这三个数，才能回答"能不能给别人用"。
第三优先：找一个真实用户跑一周。 这是唯一能打破"自己出题自己答"的办法。观察三件事：他会不会主动写、写进去的东西能不能被捞出来、捞错的频率有多高。
第四优先：降低安装门槛。 写入与向量两条链路已从 Python 搬进 Node（0.3.9）。剩余可做的是把包拆成「代码包 + 模型包」：改代码只下十六点七兆，模型只下第一次。
第五优先：补英文文档。 在真实用户验证之后再做，避免把未验证的东西翻译出去。
8.6 不打算做的
不做云端托管。 数据留在使用者本机是这个项目的前提，托管会违背它。
不做成通用记忆层。 只服务 DSH，不追求挂接所有 Agent。做通用层需要另一套工程能力，与当前目标不符。
不做商业授权。 许可证明确禁止商业使用。这一条是选择，不是遗漏。
8.7 一句话总结
这套系统在"一个人、一台机器、一份记忆"的范围内已经被验证可用；在"很多人、多台设备、长期运行"的范围内，它还没有被验证。这两者之间的距离，就是后续工作的全部内容。

A.1 从艾宾浩斯说起
1885 年，艾宾浩斯用无意义音节做自身实验，测出学习之后保持量随时间下降的曲线：二十分钟后约剩六成，一小时后约四成，一天后约三分之一，一个月后约五分之一。这条曲线有两个特征——开头掉得极快，尾巴很长。
后来的研究（Wixted 与 Ebbesen 1991 对大量保持数据的综述）指出：用幂函数拟合这类数据，比用指数函数更贴合。指数衰减在十年尺度上趋近于零，而人的记忆在十年后仍留有残余，只是难以提取。这条长尾，就是通常所说的"持久记忆"。
识海的衰减采用幂律，来源是 FSRS／DSTM 家族的间隔重复模型（该实现以 MIT 许可公开），在其基础上做了两处改动。
A.2 公式与参数
可提取度
R(t, S) = (1 + (19/81) · t / S) ^ (−0.5)
t 为距上次想起或写入的天数，S 为稳定性（天），可理解为"可提取度掉到约九成所需的时间"。19/81 这个系数来自原模型，作用是让曲线在 S 处经过一个固定点。
初始稳定性
S₀ = 0.5 + 50·imp² + 20·salience + 8·|affect|
imp 为重要度，salience 为显著度，affect 为情绪强度。原模型此处系数为 20 与 8，本实现放大为 50 与 20。原因写在代码注释里：按原系数，重要度 0.6 的记忆初始稳定性只有约 12 天，九十天后可提取度掉到 0.6 以下——对"一个人记了三个月的事"而言过短。放大约 2.5 倍后，重要度 0.6 约 30 天，重要度 0.9 约 60 天。
被想起时的增长
S' = S · (1 + 1.2·(1−R)) · (1 + 0.4·(1−D))
R 越低（越费劲想起来），S 涨得越多。这是间隔重复研究中的"合意困难"效应：勉强想起来的记忆，比轻松想起的记得更牢。D 为难度。
显示亮度
界面上的亮度取 R^2.5，并设 0.06 下限。原因是一千条记忆平铺在星图上时，若直接使用 R，整体会偏亮，看不出差别；取 2.5 次方压缩后，明暗层次才显现。这一处理只影响显示，不影响检索与归档——归档判断使用未压缩的 R。

A.5 结果说明
第一，一个月内几乎不衰减，这是刻意的。 三十天时仍有 129 条处于清晰档。衰减的作用不是"尽快忘掉"，而是"把长期不被提及的内容排序往后放"，因此前段必须平缓。
第二，一年之后没有一条进入"快没了"。 因为可见亮度的下限设为 0.06，加上五档最低档的门槛，最坏情况是落到"影子"，不会归零。这与"记忆可以难以提取，但不消失"的设计目标一致。
第三，重复命中会把记忆拉回清晰，而且越往后越稳。 条件二里，同一批记忆每三十天被提起一次，一年后全部回到清晰档。中间出现的回落（90 天时 53 条、180 天时 137 条）不是异常，而是"距上次被想起多久"在起作用：清晰度取决于距离上次命中的间隔，与总年龄无关。这正是设计想要的行为。
第四，这条曲线解释了一个常见疑问：为什么隔了很久的事，提一句还能想起来。因为它在数据里没有被删除，只是权重被压低；一旦命中，稳定性按"费劲想起"的规则增长，反而比没沉下去过更容易记住。
A.6 这次实验不能证明什么
第一，样本是合成的。 二百条记忆的结构来自真实分布，但它们不是真实发生的事，没有真实的重复与遗忘过程。
第二，参数未经真实数据拟合。 S₀ 与增长公式的系数来自公开的间隔重复模型，我只改了两处并记录了理由，但没有用自己的使用数据反过来校准。
第三，真实库的年龄不足以验证。 截至本文写作时，主库一百五十五条记忆的年龄在零到一点六天之间，全部处于清晰档。真实衰减尚未发生，本附录提供的是模型行为，不是观察结果。
第四，没有对照组。 要证明这套参数比另一套参数更接近人的记忆，需要真人盲评：给同一批旧事，比较系统判定的档位与当事人的主观感受。这一步没有做。

附录 B　论文：论 AI 陪伴系统中的记忆与情绪耦合
摘要
当前多数"AI 记忆"方案把问题定义为存储与检索：如何把更多信息存下来，如何更准地查出来。本文提出一个不同的判断：制约 AI 陪伴体验的，不是记忆容量，而是取舍机制。识海系统据此做出了三项设计选择——以遗忘曲线代替全量保留、以情绪状态作为检索权重、以单用户绑定代替共享记忆库——并在 34 轮自动化测试中取得 660/660 的检索命中与零反例泄漏。本文亦说明该设计的边界与尚待验证之处。
关键词：AI 记忆；情绪计算；遗忘曲线；陪伴系统
一、问题的提出
大语言模型有一个结构性缺陷：它没有过去。每次对话结束，上下文清空，下一次开口时它是一个信息完备却一无所知的实体。
针对这一点，工业界的主流回答是"长期记忆"：把用户说过的话、偏好、历史提取成结构化条目，需要时再检索回来。这条路线上已经有相当成熟的工作（如 Mem0、Zep、Letta），它们在抽取质量、图结构、跨会话一致性上都做得比本文所述的系统更完备。
但这条路线隐含了一个未经检验的前提：记忆的价值等于其容量与召回率。
本文认为这个前提是错的。理由有三。
第一，未被使用的记忆不是记忆。一个库里存了八百条，而每一轮对话只能注入三五条，那么真正影响行为的既不是八百，也不是召回率，而是那三五条怎么被挑出来。
第二，被全量保留的记忆会失效。人对过去的经验是衰减的：常被提起的越来越清晰，久不触碰的逐渐模糊。一个所有条目同等权重的系统，恰恰失去了人最核心的能力——知道什么重要。
第三，记忆与情绪不可分离。同一件事，心情好的时候想起的是暖的一面，心情差的时候想起的是疼的一面。把情绪排除在外的记忆系统，只能做到"记全"，做不到"像一个人"。
据此，本文的中心论点是：AI 陪伴系统的记忆设计，其核心不是容量，而是取舍；而情绪状态是取舍的自然判据。
二、分论点一：没有取舍的记忆等于没有记忆
论据一（系统约束）。设一个记忆库有 N 条，每轮可注入 k 条（k 远小于 N）。则系统的全部表现由选择函数 f 决定，而非 N 决定。扩大 N 只在 f 有效时才有收益。
论据二（实践观察）。识海系统在早期版本中曾出现这样的现象：同一条事实以两种措辞被写入两次，注入时两条并排出现。用户看到后的反应不是"它记性好"，而是"它在敷衍"。这说明记忆的呈现质量直接影响信任度，且与容量无关。
论证。识海为此引入了两项取舍机制：
其一，注入时去重。判据为"去掉"第 N 回"这类时间后缀后，前 20 个汉字相同即视为同一条"，保留最近写入者。实测每轮稳定挤出 1 条重复。
其二，分层容量上限。核心层 7 条、关系层 20 条，超出则按权重淘汰；核心层按轮次轮换，避免永远是同几条占据注入位。
小结：取舍机制不是优化项，是记忆系统的定义性部分。
三、分论点二：情绪是取舍的判据
如果取舍需要判据，那么这个判据从何而来？
纯检索系统给出的答案是"相关度"——字面匹配、向量相似度、图距离。这在事实性问答上有效，但它无法回答一个问题：两条同样相关的记忆，该提哪一条？
本文主张：由情绪状态回答。
论据一（设计）。识海维护两套状态：稳定的性格底子（八维）与随事件波动的当下（51 种情绪）。两者合成一个权重，参与三处计算——检索排序、遗忘速率、注入内容的选择。
论据二（可观测结果）。同一句"我今天腰疼得站不住"，在记忆库包含"上个月搬货架闪了腰"的情况下，系统注入的是与"硬撑"相关的经历而非通用建议；而在另一个空库中，注入为空。这意味着"提不提那件事"由库内容与当前状态共同决定，而非由问题字面决定。
论据三（遗忘）。未被触碰的记忆按幂律衰减：显示强度 R^2.5，其中 R 随时间增长而下降。但被检索、被点开即重置计时。这使"重要"成为一个动态属性：不是写入时标注的标签，而是被反复需要的程度。
反驳与回应。可能的反驳是：情绪权重引入噪声，会降低事实检索的准确率。
回应：这个反驳成立，但只对"事实型检索"成立。识海的做法是把两者分开——事实、规矩、承诺、禁区不参与衰减，永远保留；只有经历类记忆参与衰减与情绪加权。换言之，情绪不影响"你叫什么"，只影响"从哪件事说起"。
四、分论点三：一对一不是产品口号，是架构要求
论据一（隐私）。记忆库若共享，则任何一次注入都可能泄露他人信息。识海的做法是按识海（库）隔离，库与窗口绑定，跨库不注入。
论据二（一致性）。共享库会导致"它到底在跟谁说话"的身份混乱。一对一是身份一致性的前提。
论据三（可验证）。该属性可被测试：沙箱库中的内容不得出现在其他库的注入中。此为自动化测试的固定断言项，34 轮均通过。
小结：一对一并非营销层面的"专属感"，而是隐私与一致性的工程后果。
五、边界与未完成
本文主张的三项设计，其验证存在明确局限，必须说明：
其一，测试样本单一。34 轮测试的题目由作者本人编写，非第三方用户真实使用数据，存在自我确证风险。
其二，缺乏基线对照。未在同等条件下对比"去掉情绪模块"的系统表现，因此无法量化情绪耦合的实际增益。
其三，规模未验证。数百条记忆上有效，数万条量级下的检索延迟未测。
其四，结论的适用范围。本文讨论的是陪伴型场景；对事实型知识管理，全量保留与高召回率的传统方案更合适。
六、结论
本文的结论可归纳为一句：记忆系统的难点不在于记住，而在于知道什么值得想起来。
"能查到"与"会去查"是两件事。前者是检索问题，后者是判断问题。当前多数方案解决了前者，把后者留给人。
识海尝试把后者部分交给机制：用遗忘表达"重要与否"，用情绪表达"从哪说起"，用一对一保证"说的只是你"。这一尝试在自动化测试中表现稳定，但缺乏独立验证，其实效仍有待第三方使用数据检验。

附录 C　识海是怎么验的（方法论）
写这一节的原因：光有数字，别人没法判断数字真不真。这一节交代题目从哪来、指标怎么定、什么情况算数、什么情况自己作废。
里面有几个我们自己的翻车，留着，因为翻车恰好说明规矩是硬的。
一、验的东西是什么
不是"能不能搜到"这种模糊说法，是具体一件事：
这一轮她交给模型的那段正文里，到底有什么。
这段正文（注入）是插件每轮拼出来的：她这会儿的心情、几条核心记忆、跟这句话相关的几条、最近自己想起的旧事。模型看不到别的。所以验注入，就是验她"记得什么"。
二、题目从哪来
三条硬规矩：
不许自己编题。编出来的题会顺着实现写，最后验的是编题的人。
用他真说过的话。从原始聊天记录里直接抽，一个字不改。
一半题锁起来。改参数只看一半，另一半一开始就不许看，最后只见一次。
三、指标怎么定
一开始定"命中率"——目标记忆排第几。后来发现这个指标骗人。
因为注入正文里，核心层固定排在最前，目标排第五第六也算给了模型。真正的指标是两条：
覆盖率：该想起的那条，出现在正文里没有（不管排第几、哪一段）。
噪声：问界面、按钮、进度这类正事时，有没有硬塞旧事进来。
覆盖率低她会显得忘事，噪声高她会显得心不在焉。这两个是相反方向，要一起看。
四、自己作废的三次（留着）
第一次，题目是机器拼的。拿记忆里的字随机拼问句，命中 5%。看着像系统烂，其实是题烂——拼出来的是"一傻地""觉绝睡"这种不是人话的东西。作废。
第二次，看完失败项再改参数，然后拿同一批题验收。调的那半从 40% 涨到 80%，锁起来那半一条没动。这就是背题。作废。
第三次更难看。我声称"撤回了两处无效改动"，撤回之后覆盖率从 80% 掉到 60%——不是改动无效，是我把"排名没变"错当成"白改"。差点删掉真正有用的东西。这一条记住：改动的效果要看覆盖率，不能只看排名。

10.4 关系、承诺与挂念
relationlog：关系历史。状态机每次现算会丢过程，这里把「怎么变过来的」留下来。
absence：挂念与疏远，两条轴解耦——多久没说话，和心里想不想，是两件事。
preoccupations：心事，最多三件。人心里不会挂一百件事，是两三件反复转。
conflict 与 contradict：同一个事实键允许多版本并存，但必须有人标出哪句和旧话打架。
10.5 表达与自我
think：第三层「真的想一句」。边界写死：插件里没有模型 API，想靠宿主。
thinkops：想事情有十种动作，一张表；每种动作有判据，不许混着用。
selfmode：自心三档开关，low 全停，其余两档按需。
replycheck：回看她的上一句，决定要不要自检重说。
retry-mode：自检两种模式，instant 立刻推一条「重说」，另一种攒着。
stance：态度层。判定是客观的（骂就是骂），态度是她自己的——同一句骂可以是扎、是无所谓。
banter 与 banter-learn：这句是骂还是闹；用对方下一条的反应给自己改判。
hervoice：她的声音，只提示不改写；基准来自她写自己的话。
hevoice：他那种句法，压力输入生成器，用来测她扛不扛得住。
voicecheck：这句话是她的，还是谁都行——按「具体物密度」判定。
shortvoice 与 shortvoice-model：短句专用的尺子。现成的尺子量长句，短句天生吃亏。
humanness：人味能不能不用人判；把「像不像人」拆成能算的数。
aiflavor：AI 味尺子。全人的反面不是「不够像人」，是有腔。
messy：手滑语料生成器，用来造脏输入。
activity：她今天做过什么。私有念头若只从两人之间的事里长，会越来越窄。
10.6 会话、多库与对外
session：一个窗口绑一个识海，但一个识海可被多个窗口认领。
seas：识海清单：有哪些、各多少条、绑到哪个窗口。
roles：多角色与识海之间的桥，一个角色等于一个识海加一份配置。
visitor：外人进来跟她说话时的隔离与降级。
identity：身份底片，什么该永不衰减——她是谁。
10.7 热更新与运维
live：热参数，改完立刻生效。
hottext：注入里最常改的几句话，热加载，下一轮就生效。
log：审计日志，写入、检索、注入各记一行；滚动保留，不删文件。
evidence：证据层。每轮原文按天落一行，检索结果能指回原话。
uncertainty 与 tools-uncertain：记忆的不确定性——哪些条目是我编的、哪些有原话撑腰，要能标出来。
analysis：给四个问题四个答案（找同类、找反例、找来龙去脉、找该不该沉）。
tick：后台步进，每二十分钟一次，不需要模型在场。
routes：四十七个接口全在一处，页面与外部调用都从这里进。

补一句实话：上面这些大部分只有我一个人跑过，标「已实现」的还没进过第三方环境。能对外说的是「装得上、记得住、查得到、数据在本机」这四件；其余的说成「有，但没验」。

附录 J　术语表与测试清单（给读代码的人）
J1　情绪这块的名词
PAD：描述情绪的三根轴——Pleasure 愉悦、Arousal 唤醒、Dominance 支配。只给坐标，不给名字。
v / a / d：就是这三根轴。我们的 v 取 -1 到 1，a 取 0 到 1，d 表示她觉得局面在不在自己手里。
底色（baseline）：她没人打扰时的默认位置。现在是 v -0.12、a 0.10、d -0.08——偏静、偏寥寂。
回落：情绪慢慢向底色靠。每跑一格往底色走一点，不是直线跳回去。
阻尼：防止情绪来回抖。数值大了发木，小了像抽风。
极性（polarity）：这条记忆是暖的还是冷的。1 正、0 中、-1 负。
强度（arousal）：这条记忆当时有多重。0 到 10。跟情绪那根 a 不是一回事，别混。
重要度（imp）：这条记忆值不值得翻出来。0 到 1。
悬着（open）：这件事还没完。欠着的、没想通的那种。
规矩（rule）：不许忘的硬规矩。压缩也不许把它缩掉。
J2　检索这块的名词
字面：问句里的词，原样出现在记忆里。最直的一层。
词 / 必词：词是切开的片段，必词是必须命中的那几个。
实体：人名、地名、项目名。靠它把「他」和具体那条连起来。
图游走：记忆之间连着边，从命中的那条往外走一两步，看能不能走到答案。
向量 / 余弦：把句子压成一串数字，比两串数字夹角。意思近的夹角小。
候选：先用索引和向量把范围从几十万条缩到一两百条，只在这批里算分。
全文索引（FTS）：数据库自带的倒排表，按词直接跳到那几行，不用逐条扫。
分片（gram）：中文两字词（腰疼）索引认不出，得自己切成两字、三字片段塞进去。
闸 / 薄判定：挡住「证据太薄」的候选，别让一句无关的话凑成答案。
宽松准入：纯语义命中也放进来排序。代价是反例更容易被当答案。
头名 / 前三 / 前十：正确答案排第一、前三、前十的比例。三个数分开报，别只报一个。
反例：库里没有的事，问它，它该说没有。守住率就是没被编出来的比例。
等价组（also）：同一件事记了两条，答哪条都算对。合并重复之后加的。
J3　存储与工程这块的名词
双写：写一条记忆，同时落 JSON 和 SQLite。JSON 是权威，另一份是影子。
镜像：把每条记忆另导一份 Markdown，记事本能打开。只读，不回写。
WAL：SQLite 的写日志模式。写入先进 -wal 文件，主库文件的修改时间不会变——别拿时间判断有没有写。
热加载：改数字不用重启。配置几秒后自己生效。
幂等：同一件事做两遍，结果一样。备份和重放都靠它。
一键自检：一条命令跑完全部测试。十一组，任何一组红就非零退出。

附录 F　2026-11-12 修订：写入与向量都搬进 Node
一句话。这一版把写入从 Python 脚本换成 Node 内部实现，把向量计算从「本机要装 Python + torch」换成「模型和推理引擎随包发、进程内算」。使用者装完即可用，不再需要额外环境。
写入，怎么换的。原先调一段六十四 KB 的 Python 脚本，负责落盘、连边、算相似度、去重。现在这些在 Node 里重写：拿锁、造条目、连边、冲突标记、备份、原子写（临时文件改名）、放锁。退回旧路可以设环境变量 DSH_WRITER=py。
换完之后等不等价。造两个沙箱识海，喂同一批六十条：一个全程 Python 写，一个全程 Node 写。结果条数 60 比 60；十七个字段逐条比，零差异；突触 221 比 221，只在一边的零条。检索也一致：三个不同角度的问题分别查两个库，编号、分数、走的哪条规则全一样。
同时比原来强的地方。并发：六进程同时写六十条，一条不丢；锁从「建文件再写」改成「先写临时文件再硬链接挂名」，消掉空文件被当成过期锁的窗口。防重复：同标题同正文六十秒内重写，直接返回原条；写库成功后的收尾不再抛错（此前会诱导重试，一次变三条）。坏库：截断后读出空、不崩，可用备份恢复。
向量，怎么搬的。模型是 bge-small-zh 的量化版本（二十二点九兆），推理引擎是 onnxruntime-web 的 WebAssembly（十四点二兆），两者都在安装包里。Node 进程内算，不联网、不装 torch、不启服务。首次加载约零点二四秒，之后一条四毫秒，常驻内存约一百七十兆。
对准了没有。同一批问句跟原模型比，余弦相似度在零点九九一到零点九九四之间，十句全过。整库一百八十七条重算向量，旧文件已备份。头名与 fp32 模型比是 8 比 10 一致；fp32 多九十兆只换回两句，所以默认只发量化版。
怎么证明它真的不靠 Python。把 8931 端口上的 Python 嵌入服务杀掉、确认端口没人听，再查一句话——结果仍带语义分（零点五一）。这一刀切下去，「不依赖 Python」才算落地，而不是文档里的说法。
端到端补的一个缺陷。测出过「刚写的东西换个说法查不到」：新条目没有向量，向量是异步补的，只有字面完全对上才找得到。已改成写完立刻给这一条算向量（十几毫秒）。修完再验：写「自行车停在老槐树下忘了上锁」，立刻问「他的车放哪儿了忘了锁」，命中第一，语义零点六八。
规模，测到三十万条。一万条：读整库十九毫秒、检索九毫秒、再写一条六十七毫秒。三万条：读六十七毫秒、检索二十三毫秒、再写一条二百零一毫秒。三十万条：读六百五十八毫秒、检索八十九毫秒、再写一条约两秒、内存七百九十二兆。分界在三十万前后；一百万会到 GB 级内存和数秒读库，那要换存储，属另一个项目。
三十万条压出的一个真崩。第一次跑三十万条，写一条直接失败：Maximum call stack size exceeded。原因是我自己写的 Math.max(...points.map(...))，三十万个参数铺满栈。同一写法在别处还有两处，一并改成循环。这条记下来：凡是把大数组展开进 Math.max，就是定时炸弹。
安装怎么变。包从十七点九兆涨到约五十五兆（解压后约五十七兆）。装成两个包发：代码十六点七兆、模型十九点四兆——改代码只让用户重下前者。干净用户目录实测：从零写三条、建向量两百六十四毫秒、换个说法能查到；别的盘、中文加空格、超长路径三种都通过。
跨平台修的两处。一，代码里有两处用反斜杠拼路径，在 Linux 与 macOS 上那是文件名的一部分，目录根本不存在，已改成 join(homedir(), …)。二，找 Python 只认 python，Linux 上叫 python3，候选表已补。这两处是扫出来的，不是跑出来的——Linux 与 macOS 仍未实测，只能算扫干净了。
还没做的。一，陌生机器真装一遍（本机验过，别人没验）。二，Linux 与 macOS 实跑。三，检索别再动小零件——今天试了四样，成两样废两样，剩下的空间要换机制（跨编码器重排，或让模型自己挑）。定稿数：真实检索头名 63%、前三 68%、前十 70%、反例守住 88%。只看向量层是 61/82/95，两组不是一回事。

附录 G　2026-11-12 傍晚：检索的真实底数（补附录 F 之后的六小时）
这一节为什么非写不可。附录 F 报的数字是「只看向量层」的：头名 46%、前三 74%、前十 82%（旧集），后来提到 61/82/95。用户真正看到的不是向量层，是四层合起来的结果。傍晚第一次把整条链路拿九十道题量出来，头名只有 19%。差四十个点，说明之前对外说的准头，和实际体验不是一回事。
差在哪：不是向量，是中间那道闸。代码里只留「字面或词对得上」的候选，纯语义候选在排序之前就被筛掉了。所以大多数问句只剩一条，前十等于头名。向量算得再准，进不了排队也没用。
改法与实测。加「宽松准入」：字面没对上、但语义 0.50 以上的候选，也放进来参与排序。同一批九十道题、走真实检索工具：头名 19%→60%，前三 21%→72%，前十 21%→79%。放宽到 0.45 头名掉回 58%，所以定在 0.50。
代价。三十三条「库里没有」的问题里，被当成真答上的从一条涨到七条。这是拿「少一点瞎答」换「多三倍的答上」。以后想压误命中，该动排序权重，而不是继续在闸上拧。
别名进向量：留出集头名 45%→70%。原先向量只用标题加正文，别名（别人会怎么问）根本没进去，而库里只有三成八的记忆带别名。把别名拼进向量后：同一批题，不带别名头名 45%、带别名 70%；前十 70%→100%。另写了二十条全新问法做留出集，写的时候没照别名，仍然从 45% 涨到 70%——不是背答案。
自动生成别名：实测是负分。别名是人手写的，别人装完没有，享受不到那二十五个点。所以试了规则生成，抽出来是「老古董的降维震撼是怎么回事」这种，不是人话。在沙箱海把别名清零（等于别人刚装完）跑留出集：头名 45%；规则自动补完掉到 35%。比不加还差——笨问法把向量往错处拉。结论：生成器只出候选审阅稿，不自动写回。能生成不等于该生成。
反例闸。留下来的如果每条都只是弱语义（语义 < 0.55、字面 < 0.35、没有必词与实体），就判成「库里没有」，返回保底一条并标注「凑出来的」。验：「他手机号是多少」「他的身高是多少」都变成了保底，不再像正常命中；「他腰疼那次我说了什么」仍正常命中。

附录 I　2026-11-12 夜里：存储换底、镜像可导出、一键自检
这一节补什么。附录 H 写的是检索四样实验。之后又动了存储：SQLite 双写、Markdown 镜像、导出工具、一键自检。这一节把它们写清，也把踩的坑写清——有些坑比功能值钱。
一、SQLite 双写（成了）。写记忆时同时落 JSON 和 SQLite。走的是写库总入口，两秒内的多次写合成一次镜像；失败只吞掉，不影响这次写入——JSON 仍是权威。超过五千条就不自动镜像了，那个规模该显式重建。
二、一致性分两档。正文、标题、别名、类型、重要度、是否死掉——结构字段必须零差异。强度、情绪、悬着状态会随心跳漂，单独统计。现在真库：结构零差异、漂移零处。

四、Markdown 镜像（导出，只读）。每条记忆一个 .md，带编号、别名、类型、重要度、情绪、分类、实体，记事本能直接开。真库导出 198 个文件。**默认只读**——在文件里改字不影响识海，改记忆走页面里那条的编辑。

六、一键自检。一个命令跑完五组检查：写入二十一项、词闸五项、双写八项、候选六项、一致性一组。今天靠它才发现一致性那块早就红了。
三个坑，都写下来。一，插件工具注册失败不拦启动，只往日志写一行——界面正常、探针全过，不代表工具都在。二，插件里并存两个写库模块，改错一份会白忙一场——改任何「看起来只有一份」的东西，先查谁 import 它。三，SQLite 开着 WAL，主库文件的修改时间不会随写入变——拿时间判断「有没有写」会误判。
