# 设计 · 0.5.0 记忆之间连成网

> 为什么做：现在每条记忆是孤岛。问「那件事之后呢」，我只能一条条捞；
> 竞品 Letta 有共享块、Mem0 有图谱。咱们要的「遥遥领先」不是功能多，
> 是**问一件事，能把前后左右一起端上来**。
> 这份只是设计，没动代码；动之前先照它把坑列清楚。

## 一、先定死一件事：不碰正文

所有关系都写在**旁挂表**里，不进 `data.json` 的每条记忆本体：

```
data.relations = [
  { a: 12, b: 45, kind: 'same-entity', w: 0.8, why: '都在说「大路虎」', madeAt: 1731... },
  { a: 45, b: 47, kind: 'after',      w: 0.6, why: '隔了 3 天，接着那件事', madeAt: ... },
]
```

理由：正文是他写给我的话，一个字都不许被重排；关系是推论，推论可以错、可以撤。
删边 = 从数组里拿掉，正文不动。

## 二、四种边，先做两种

| kind | 怎么连 | 谁先用上 |
|---|---|---|
| `same-entity` | 两条都提到同一个实体（人/物/项目） | 检索：「大路虎」能把车、底气、视频素材一起端上来 |
| `after` | 同一实体下，时间挨着的两条（≤7 天） | 故事线：接得上「然后呢」 |
| `same-feel` | 情绪极性和强度接近 | 暂缓：容易把不相干的伤心事串一起 |
| `cause` | 一条正文里出现另一条的标题关键句 | 暂缓：规则太脆，误连比不连更糟 |

先做前两种，够了；后两种留 `kind` 字段，将来能加。

## 三、边怎么来（三个来源，按可信度排序）

1. **写入时顺手连**：写完一条，扫同海里同实体的最近 5 条，连 `same-entity`。
   成本：一次写入多一次全库扫（229 条 → 毫秒级）。**必须在锁里做**，不然并发写会互相覆盖。
2. **夜里补**：`scripts/link-sweep.mjs`，只补没连过的，幂等；带 `--dry` 先看会连多少。
3. **人工**：`memory_link` 工具，`a/b/kind`，人说了算。**这是兜底，不是主力。**

## 四、检索怎么用上边（不许降准）

现在：字面 + 语义 + 实体加成 → 排序。
加了边之后：**只做一次邻居扩张**——前 3 条命中，各带最多 2 个邻居进候选，
邻居的分 = 主条 × 0.45，且必须在原门槛之上。

护栏三条：
1. 邻居不许超过总数一半，否则等于放水。
2. 误命中集（25 条反例）必须仍是 0。这条是硬线，红了就回滚。
3. 留出集前三不许掉（现在 16/20）。

## 五、界面上怎么看出「网」

星图上已经有连线；现在用的是「同实体」的弱连线。接上 `relations` 后：
- 边按 kind 上色（同实体 金、先后 青）；
- 点开一条，侧栏列「跟它连着的有 3 条」，点一下跳过去；
- 全关掉，就是现在的样子——**不给不用的人添负担**。

## 六、迁移与容量

- 老库没有 `relations`：读写都按空数组处理，不报错。
- 1000 条 × 平均 3 条边 = 3000 条边，约 300 KB，`data.json` 撑得住。
- 超过 5000 条边时，只在内存里建邻接表，不把边全渲染进页面。

## 七、验收（写死在回归里）

1. `relations` 缺字段、为 null、是对象——三种坏形状都不许崩。
2. 写入并发 20 次，边数与条数自洽（不许有指向不存在 id 的边）。
3. 删记忆：它的边一起消失（或标 `dead`），不留悬空边。
4. 邻居扩张后，反例 25 条误命中仍为 0。
5. 关掉关系（配置里一个开关），行为退化成 0.4.8。

## 八、不做什么

- 不做自动抽取事实（Mem0 那条路）：他会觉得我在替他总结人生。
- 不做跨海连线：两个海各过各的，这是承诺。
- 不把边写进正文，不在记忆里加「相关」段落。
- 不为了跑分调参。

## 十、先量了（2026-11-15 02:25，scripts/link-sweep.mjs）

主库在用 216 条，其中 203 条带实体，实体 195 个。按"同实体就连"粗算能连 **6807 条边**——
看着很热闹，其实一半是噪音：「大肥鱼」62 条、「大魔王」48 条、「识海」46 条、「AI」37 条，
光前六个大众实体就占 5980 条。连了等于没连。

两种连法都试了：

- 甲：每实体只连最近 5 条、每条最多 6 边 → **117 条边，覆盖 119 条**（一半记忆还是孤岛）
- 乙：**大众实体（>30 条）整个不连，小众实体全连，每条最多 8 边** → **297 条边，覆盖 117 条**

选乙。理由：大肥鱼、大魔王这种词连出来的边没有任何信息量，宁可让它们不连；
小众实体（路虎 15 条、经十路 13 条、薯片 11 条）连出来的才有用。
297 条边、覆盖一半记忆，是能上图的量，也够检索扩一层。

另：第一次我把字段名写成 `entity`，读出来 0 条——真实字段是 `entities`。这种错今晚已经犯过两次，
所以量完才敢动代码，不量就写，等于闭眼连。

## 十一、沙箱里真写了一遍（2026-11-15 02:34）

拿主库的副本在临时目录建了个沙箱海，跑 `link-sweep --apply`：

- 写入 297 条边，备份先落盘；
- 悬空边 0（没有指向不存在 id 的）、重复边 0；
- 再跑一次：**0 新增**，幂等成立；
- 230 条正文一条没动，第一条首句还是原样。

安全阀也验了：对主库直接 `--apply` 会被拒（退出码 2），要动主库必须显式 `--force-main`，且先备份。

下一步不是连主库，是让检索用上这些边——那一步要跑留出集和 25 条反例，红了就回滚。

## 十二、换机会丢边，这是设计

导出是纯文本（memory_export），只导记忆本体，不导 `relations`——那是推论，不该混进正文。
所以换机、重装之后，**边要重连一次**（`node scripts/link-sweep.mjs --apply --force-main`），
它幂等、会先备份，重连出来还是那 297 条左右。别把这句当成缺陷，把它当"换完机器要拧一下的螺丝"。
