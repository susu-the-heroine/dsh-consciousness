## 第二轮 · 写入模块逐行（writer-js，432 行，已读完）

### 1. 层判定靠关键词，含「我」就可能进 core
SELF_WORDS 里有「我」，MILESTONE_WORDS 里有「第一次」；两句凑齐就判 core。
现象：任何「我今天第一次吃这个」都可能被当成核心记忆，永不沉底。
严重度：高（污染核心层，且不可逆——沉底靠层）。

### 2. 冲突几乎检不出来
findConflict 要求：有共同实体 + 同分类 + 极性相反 + 文本相似 ≥0.3，且「极性为 0 直接返回」。
现象：绝大多数条目 polarity 是默认 0，等于冲突检测对它们完全关闭。
严重度：高（决定「改口」能不能被发现）。

### 3. 相似度用二元组，短文本假高分
sim = 两字片段交集 / 较短一侧数量。
现象：六个字的短句互相容易接近 1，冲突与连边都会误判；长文本又偏严。
严重度：中。

### 4. 主库节点 id 写死
HUB_ID = 119，连边时特殊对待。换一个库、换一个用户，没有 119 这条，逻辑照跑但含义变了。
严重度：中（给别人的库用会怪）。

### 5. 写入是 O(条目数)，还会重试 200 次
挑坐标时最多试 200 次，每次都扫全库找碰撞（0.02 半径）。
现象：一万条以后每写一条都要扫一万条 × 最多 200 次。
严重度：中高（写入慢随库增长）。

### 6. 去重要求标题完全一致
findDuplicate 先比标题，标题不同直接跳过。
现象：同一件事换个标题写两遍，库里两条并存。
严重度：中。

### 7. 影子实现把原版的毛病一起抄了
注释多处写「原版就是这么算的」「先照抄，等跑齐了再统一」。
现象：Python 时代的行为被完整继承，包括已知的不一致。
严重度：中（继承的是技术债，不是功能）。


## 第三轮 · 检索主链路（tools.js，已读 1174–1423）

### 1. 调试落盘其实从来没写成（真 bug）
第一段 try 里定义了 os3，第二段 try 里又用 os3；跨块 const 取不到，抛错被空 catch 吞。
证据：那两份调试文件最后一次写入是 11-11，而慢查询日志到今天还在写。
严重度：中（不影响线上，但等于「排障工具早就瞎了」）。

### 2. 回答里会漏出调试串
「为什么是这条」里有一条拼的是「词[...]必[...]」，那是给开发看的，现在会跟着结果出去。
严重度：中（用户能读到内部词表，且难懂）。

### 3. 两处线性查找，条目一多就 O(n²)
精确命中与实体两路都在对 scored 里做 find，每条候选查一次。
严重度：中（一万条以上会明显）。

### 4. 实体命中给 0.85 死分
只要查询里出现某实体名，直接抬到 0.85，压过大多数真实语义分。
严重度：中（人名地名多时，排序被硬拔）。

### 5. 稀有词要全库扫两遍
算必命中词时，对每个查询词扫一遍全库；与后面的主循环重复。
严重度：中高（慢查询来源之一）。


## 第四轮 · 检索主链路续（tools.js 1424–1563）

### 1. 同一个探测函数被调两次
向量候选那块先按三千条门槛探一次，后面又按一千二百条门槛再探一次，两次调用同一函数。
后果：大库每问多算一遍；两个门槛还打架，小库走哪个看运气。
严重度：中。

### 2. 注释与代码不一致
注释写短句阈值放到 0.22，代码写的是 0.15。
严重度：低，但这种不一致会误导后来人。

### 3. 分词函数在同一段里复制三份
稀有词表一份、查询词一份、循环里再来一份；循环里那份是每条候选都重算。
严重度：中高（慢查询来源）。

### 4. 候选循环里又用了线性查找
向量命中后要去 scored 里找已有的那条加分，还是 find。
严重度：中。

### 5. 稀有词表缓存 key 很弱
用海名 + 条数 + 第一条的 id 与标题长度拼 key，改内容不改长度时不失效。
严重度：低（六十秒后自然过期）。


## 第五轮 · 检索主链路续（tools.js 1564–1703）

### 1. 标题兜底给了 8 分，等于直接霸榜
字面兜底里，只要标题包含整句问话，就给 score = 8；正常分数都在 0～1.5 之间。
后果：这一条绕过所有门与重排，必然第一；问句越长越容易命中——和直觉相反。
严重度：高。

### 2. 纯语义命中的加减规则靠标题正则
意图判成「指令」时，只要标题里有「成了/跑通/上线」这类词就砍半。
后果：同一句话，标题用词不同，排序差一倍。
严重度：中。

### 3. 一堆硬编码权重
冲动层 0.22、图游走至少两个查询词、语义进入门槛 0.15/0.35/0.75、短句阈值 8 字。
严重度：中（调参靠改代码）。

### 4. 排序在同一问里排了五次以上
每加一路候选就整体重排一次，库大时是纯浪费。
严重度：低。


## 第六轮 · 检索主链路续（tools.js 1704–1843）

### 1. 每搜一次就整库写盘 + 备份
命中之后会强化被想起的条目，然后备份整库、再写整库。
后果：搜索变成写操作，高频或并发时 IO 放大，八路并发会互相覆盖。
严重度：高。

### 2. 搜索路径里同步补向量
写完库居然还等着补向量（一次最多八条）。
后果：搜索耗时被向量计算拖住；向量服务慢时，问一句要等。
严重度：中高。

### 3. 热加载用带时间戳的模块地址
每次搜索都 import 一个带时间戳的新地址，等于每次都重新解析一份模块。
后果：模块缓存永远不命中，V8 侧内存随次数增长。
严重度：中高（长跑会涨内存）。

### 4. 一个开关管三件事
「实体」那个开关同时管实体、图游走、模式补全；低档一关，三件全没。
严重度：中（档位语义与实际能力不符）。

### 5. 同一道闸抄了三遍
图游走、模式补全各写一遍“至少两个查询词 + 必命中词”的检查。
严重度：低（改一处漏两处）。


## 第七轮 · 检索主链路续（tools.js 1844–1983）

### 1. 片段重排把分数排序整个覆盖了（真 bug）
问句去掉标点后 ≥8 字时，会按“两字片段命中个数”重排，排序函数只看命中个数，不看分数。
后果：命中片段多但分数低的条目，会压过分数高的；长问句尤其明显。
严重度：高。

### 2. 出口兜底又给 2 分并直接插到第一
整句对得上就 unshift 一条 score=2 的，正常分数都在 1.5 以内。
后果：和标题兜底那处（8 分）同类，两条越级通道各自绕开全部闸。
严重度：高。

### 3. 拼音通道分数偏高
拼音命中给 0.5 加相似度，能压过正常候选。
严重度：中。

### 4. 一次搜索最多写三次库
强化一次、关闭未了一次、标记悬着一次，每次都备份加整库写。
严重度：高（叠加第六轮那条，IO 更重）。
